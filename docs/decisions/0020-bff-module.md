# 여러 도메인을 모아 보여 주는 조회 API는 맨 위의 `bff` 모듈에 둔다

## 맥락

강사의 회원 목록 · 상세 응답에는 회원 정보와 수강권 카드가 같이 들어간다(DEC-0010). 회원은 `membership`, 수강권은 `entitlement` 모듈이다.

- 의존 방향은 외래 키 방향을 따라 `entitlement → membership → instructor`다. 수강권을 등록할 때 회원 행을 잠그고 상태를 확인해야 해서 `entitlement`가 `membership`을 부른다
- 회원 응답에 카드를 넣으려고 `membership`이 `entitlement`를 부르면 의존이 순환해 Spring Modulith 검사(`ModularityTests`)가 실패한다
- 카드의 남은 횟수 · 상태 · 순서는 수강권 규칙이라 `membership`이 `entitlement` 테이블을 직접 읽어 계산하면 규칙이 두 곳에 생긴다
- 기능 0002의 회원 화면(`/m/{token}`)은 회원 · 시간표 · 수강권 카드 · 예약 네 도메인을 한 응답에 담는다. 같은 문제가 더 크게 반복된다
- FE는 React SPA이고 브라우저가 `api.`를 직접 부른다. FE 쪽에 조립용 서버를 두지 않는다(DEC-0008)

## 결정

1. 최상위 패키지 `com.fitlink.bff`에 `bff` 모듈을 둔다. 도메인이 아닌 기술 모듈이다(`auth`와 같은 성격, BE-ADR-0016)
2. **여러 도메인의 데이터를 한 응답에 모으는 조회 API**는 `bff`에 둔다
   - `bff`는 각 도메인 모듈 루트의 `{모듈}Facade`만 부르고 받은 `Info`를 응답 모양으로 합친다
   - 응답 하나가 한 도메인의 데이터만 쓰면 그 도메인 모듈에 둔다
   - 같은 URL이라도 쓰기(POST · PATCH 등)는 도메인 모듈, 여러 도메인을 모으는 읽기(GET)는 `bff`에 있을 수 있다. 예: `/instructor/members`의 POST는 `membership`, GET은 `bff`
3. `bff`는 테이블을 갖지 않고 SQL을 쓰지 않으며 쓰기 API를 두지 않는다. 규칙(남은 횟수 계산, 카드 순서 등)은 각 도메인이 계산해 `Info`에 담아 주고, `bff`는 짝짓기 · 묶기만 한다
4. `bff`에 의존하는 모듈은 없다. 그래서 모듈 루트에 `Facade`를 두지 않는다
5. 여러 Facade를 부르는 조회는 `bff` 서비스 메서드 하나의 읽기 전용 트랜잭션으로 묶어 같은 시점의 데이터를 본다(REPEATABLE READ). 회원 목록처럼 여러 건이면 도메인 Facade가 id 목록을 받아 한 번에 돌려줘 쿼리 수를 고정한다(N+1 방지)
6. 안의 폴더는 BE-ADR-0017 그대로(`controller` · `dto` · `service`)다. 하위 폴더는 Spring Modulith가 모듈 내부로 보므로 다른 모듈이 `bff`에 의존하면 `ModularityTests`가 실패한다(`auth`와 같다). 따로 규칙을 더하지 않는다
7. 쓰기 API의 응답은 그 도메인 데이터만 담는다(예: 회원 수정 응답에 수강권 카드가 없다). 여러 도메인을 모은 화면이 필요하면 FE가 `bff`의 조회를 다시 부른다

이 결정이 보완하는 것(이전 결정을 고치지 않고 내용을 더한다):

| 결정 | 대체되는 부분 |
|---|---|
| BE-ADR-0011 | 결정 1의 "도메인 6개를 최상위 패키지로 나눈다"에 기술 모듈 `bff`를 더한다(`auth`처럼 도메인 수에 넣지 않는다) |

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 의존성 역전: `membership` 루트에 카드 조회 인터페이스를 두고 `entitlement`가 구현 | 카드 모양(Info)을 회원 모듈에 정의해야 해서 수강권 변경이 회원 모듈 파일까지 번진다. 0002처럼 네 도메인을 모으면 인터페이스가 계속 는다. 루트 이름 규칙에 새 종류도 필요하다 |
| 조회를 `entitlement`로 옮김(필요한 모듈을 다 아는 도메인 모듈이 조립) | 수강권 모듈에 회원 목록 API가 생긴다. 응답에 예약 정보가 필요해지면 다시 `booking`으로 옮겨야 한다 |
| 방향 뒤집기: `membership → entitlement`, `entitlement`는 `member`를 SQL로만 잠금 · 확인 | "의존 방향 = 외래 키 방향" 원칙을 깬다. 다른 모듈 테이블을 SQL로 잠그면 경계 검사가 보지 못한다 |
| FE가 API 두 개를 불러 합침 | FE와 합의한 응답 모양(회원 응답에 카드 포함)이 바뀐다. 화면마다 요청이 두 번이고 그 사이 데이터가 바뀌면 어긋난다 |
| FE 쪽 BFF 서버 | DEC-0008(브라우저가 `api.`를 직접 호출, FE 호스팅은 중계하지 않음)과 배포 구조를 바꿔야 한다 |

## 대가

- 같은 URL의 코드가 두 모듈에 나뉜다. "쓰기는 도메인 모듈, 여러 도메인을 모으는 읽기는 `bff`"로 찾는다
- 회원 추가 · 수정 응답에 카드가 없다(처음 설계는 상세와 같은 모양이었다). 화면이 수정 뒤 카드를 보여 주려면 상세를 한 번 더 읽는다
- 도메인 Facade에 조회용 메서드와 `Info`가 는다
- 처음에는 회원 목록 · 상세처럼 단순한 조립뿐이라 모듈 하나가 과해 보일 수 있다. 0002 회원 화면이 들어오면서 제 역할을 한다
- 기능 0001 Phase 3에서 `membership`에 만든 회원 목록 · 상세 GET을 `bff`로 옮긴다(동작은 같다)
